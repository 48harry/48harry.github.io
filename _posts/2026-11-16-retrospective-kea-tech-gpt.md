7월에 만든 토이 프로젝트 **KEA Tech-GPT**를 11월에 다시 열었습니다.
포트폴리오로 쓰기 전에 제대로 다듬어 보려던 것인데, 생각보다 고칠 게 많았습니다.
이 글은 그 과정에서 무엇을 발견했고 무엇을 배웠는지 정리한 회고입니다.

- 코드: [48harry/KES-tech](https://github.com/48harry/KES-tech)

## 어떤 프로젝트였나

중소·중견 가전 기업의 특허 담당자를 위한 AI 비서입니다.
사내 문서(PDF)를 올리면 그 문서와 특허청 KIPRIS API를 함께 검색해 답하고, 대화 내용을 보고서로 정리해 줍니다.

구성은 이렇습니다.

- **에이전트**: LangGraph로 `reason → tools → verification` 흐름을 만들고, Gemini 2.5 Flash가 도구를 골라 부릅니다.
- **문서 검색**: 업로드한 PDF를 FAISS에 넣어 검색합니다.
- **외부 검색**: 문서에 없는 특허는 KIPRIS Plus API로 찾습니다.
- **UI**: Streamlit으로 만들었습니다.

특허 업무에서 가장 위험한 건 AI가 **그럴듯한 특허번호나 청구항을 지어내는 것**입니다.
그래서 처음부터 "근거가 없으면 지어내지 않는다"를 핵심 목표로 잡고, 검증 노드를 두었습니다.

7월에는 발표까지 마쳤고, 데모도 잘 돌아갔습니다. 적어도 그렇게 보였습니다.

## 다시 열어 보니

넉 달 뒤 코드를 다시 읽어 보니 발표 내용과 코드가 맞지 않는 곳이 여럿 있었습니다.

| 발표 자료 | 실제 코드 |
|---|---|
| 5단계 파이프라인(플래너 노드 포함) | 노드 3개 |
| 신뢰도 70점 임계값 | 점수를 매기는 코드가 없음 |
| 순환 검증 루프 | 실패하면 다시 찾지 않고, 실패를 알리는 가드레일 |
| `lru_cache`로 중복 호출 방지 | 구현돼 있지 않음 |

발표를 준비하면서 "이렇게 할 것"과 "이렇게 했다"가 섞였던 것 같습니다.
면접에서 이 부분을 물었다면 곤란했을 겁니다.
그래서 하나씩 코드와 맞추거나, 발표 자료 쪽을 사실대로 고치기로 했습니다.

더 심각한 건 **"지어내지 않기"를 지키는 검증 노드에 구멍이 있었다**는 점입니다.

1. **검증 노드가 마지막 도구 결과 하나만 봤습니다.** Gemini가 도구 두 개를 동시에 부르면, 앞의 하나가 실패해도 그냥 넘어갔습니다.
2. **실패를 문자열로 판정했습니다.** 결과에 "검색 실패"라는 글자가 있는지로 판단했는데, KIPRIS는 키가 틀려도 오류 대신 HTTP 200과 빈 결과를 돌려줍니다. 그래서 키 오류가 검증을 통과했습니다.
3. **프롬프트가 지어내기를 유도했습니다.** 답변 형식에 "청구항을 반드시 쓰라"는 요구가 있었는데, KIPRIS 검색 결과에는 애초에 청구항이 없습니다. 근거가 없는 것을 쓰라고 시킨 셈입니다.

할루시네이션을 막으려고 만든 장치가, 정작 할루시네이션이 생기기 쉬운 경우에 동작하지 않고 있었습니다.

## 고친 방법

### 테스트를 먼저 썼다

7월 버전에는 테스트가 하나도 없었습니다.
이번에는 버그를 재현하는 테스트를 먼저 쓰고, 기존 코드에서 실패하는 것을 확인한 다음에 고쳤습니다. 처음 쓴 테스트 15개 중 11개가 기존 코드에서 실패했습니다.

LLM 앱을 테스트하는 방법은 이랬습니다.

- **가짜로 바꾸기**: Gemini와 KIPRIS를 미리 정한 응답을 돌려주는 가짜로 바꿨습니다. 그래서 API 키나 네트워크 없이 테스트가 돕니다.
- **실제 호출 막기**: 실수로 실제 Gemini를 부르면 테스트가 실패하도록 막아 두었습니다.

### 실패를 텍스트가 아닌 데이터로

도구가 LLM이 읽을 텍스트와 별도로 `{"ok": bool, "reason": str}` 상태를 함께 돌려주게 바꿨습니다.
LangChain의 `response_format="content_and_artifact"`를 쓰면 이 값이 `ToolMessage.artifact`에 담깁니다.

검증 노드는 이제 이 값을 보고 도구 결과를 모두 확인합니다.

- 전부 실패하면 "찾을 수 없다"고 답하게 합니다.
- 일부만 실패하면 실패한 도구와 사유를 프롬프트에 알려, 성공한 결과만 근거로 쓰게 합니다.

### 그 밖에

- **출처 표시**: 답변에 `[출처: 파일명 p.N]`을 붙입니다.
- **업로드 상태 버그**: PDF를 지워도 이전 문서로 답하던 문제를 고쳤습니다.
- **배포 경량화**: 쓰지 않는 의존성을 지워 배포 빌드에서 torch가 빠졌습니다.
- **CI**: GitHub Actions로 PR마다 테스트가 자동으로 돌게 했습니다.
- **발표와 코드 맞추기**: 발표에서 말했던 `lru_cache`를 실제로 구현했습니다.
- **스트리밍**: 답변이 생성되는 대로 화면에 나오게 했습니다.

## 평가를 돌렸더니 버그가 또 나왔다

여기까지 하고 테스트가 모두 통과하자 "이제 됐다"고 생각했습니다.
그래도 할루시네이션을 막는다고 말하려면 숫자가 있어야 해서, 평가 세트를 만들었습니다.

- **질문 20개**
  - 문서에 답이 있는 질문 10개
  - 문서에 없는 함정 질문 6개 (예: 문서에 없는 회사의 특허를 묻기)
  - KIPRIS가 필요한 질문 4개
- **자동 채점**
  - 지어낸 특허번호: 답변에 나온 번호가 도구가 가져온 근거에 없으면 지어낸 것으로 봅니다.
  - 정답 특허번호가 답변에 있는지
  - 출처를 표시했는지
  - "찾을 수 없다"고 답했는지

결과는 이랬습니다.

| 지표 | 결과 |
|---|---|
| 지어낸 특허번호 | **0/10** |
| 문서에 있는 질문의 정답 | **0/10** |

특허번호를 지어내지는 않았습니다. 하지만 **문서에 답이 있는 질문 10개를 모두 업로드 문서가 아니라 KIPRIS로 보냈습니다.**
측정할 때는 KIPRIS 키를 빼 두었기 때문에, 전부 "찾을 수 없다"고 답했습니다.
지어내지 않은 건 맞지만, 답할 수 있는 질문에 하나도 답하지 못한 겁니다.

원인은 단순했습니다. **모델은 사용자가 문서를 올렸다는 사실을 몰랐습니다.**
앱 입장에서는 화면에 업로드된 파일이 보이니 당연한 상태입니다. 하지만 프롬프트에 그 사실이 없으니, 모델은 "특허 질문이면 특허청 검색"을 골랐습니다.

그래서 매 질문의 시스템 프롬프트에 현재 상태를 넣었습니다.
문서가 있으면 먼저 그 문서를 검색하고, 사용자가 외부 검색을 직접 요청할 때만 KIPRIS를 쓰라고 지시합니다.

이 버그는 단위 테스트로는 잡을 수 없었습니다.
단위 테스트는 "도구가 불리면 제대로 동작하는가"를 확인할 뿐, "모델이 맞는 도구를 고르는가"는 실제 모델로 돌려 봐야 알 수 있었습니다.

## 예상하지 못한 벽: 무료 API 한도

평가를 돌리면서 무료 등급 Gemini API의 한도에 두 번 막혔습니다.

1. **임베딩: 분당 30,000 토큰**
   - 샘플 PDF(810쪽)를 한 번에 올리면 실패합니다.
   - 앱에는 5MB 업로드 제한을 두고 "메모리 초과 방지"라고 설명했는데, 실제 병목은 메모리가 아니라 API 한도였습니다.
   - 평가 스크립트에서는 문서를 나눠 1분 간격으로 임베딩하게 했습니다.
2. **호출: 하루 약 20회**
   - 도구를 쓰는 질문 하나에 2회가 들어, 20문항 평가가 10문항에서 멈췄습니다.
   - 배포된 데모도 같은 키를 쓴다면 하루에 10개 남짓만 답할 수 있다는 뜻입니다.

그래서 라우팅을 고친 뒤의 전체 재측정은 아직 하지 못했습니다.
수정 내용은 테스트로 확인했지만, 실제 모델이 의도대로 움직이는지는 다음 측정에서 확인해야 합니다.

## 배운 것

**1. "테스트 통과"와 "맞게 동작함"은 다르다**

LLM 앱에서 가장 중요한 동작, 곧 어떤 도구를 고르고 무엇을 근거로 답하는지는 결국 실제 모델이 정합니다.
단위 테스트는 코드를 지켜 주고, 평가는 동작을 확인합니다. 둘 다 필요합니다.

**2. 모델은 앱의 상태를 모른다**

프롬프트에 없는 정보는 모델에게 없는 정보입니다.
"문서가 업로드돼 있다"처럼 개발자에게는 너무 당연한 사실도 명시적으로 넘겨야 합니다.

**3. 실패는 구조화된 값으로 다룬다**

"검색 실패"라는 글자를 찾는 방식은 외부 API가 예상과 다르게 응답하면 바로 무너집니다.
성공과 실패를 별도의 값으로 넘기니 검증 로직이 단순해지고 믿을 수 있게 됐습니다.

**4. 발표 자료도 코드처럼 검증해야 한다**

"이렇게 할 계획"과 "이렇게 했다"를 구분하지 않으면, 나중에 그 차이를 설명해야 하는 건 결국 저 자신입니다.
지금은 측정한 숫자만 쓰고, 측정하지 않은 것은 측정하지 않았다고 씁니다.

**5. 무료 등급의 한도도 설계 조건이다**

시연 직전에 한도에 막히면 대응할 방법이 없습니다.
한도는 기능을 다 만든 뒤에 확인할 게 아니라, 처음부터 아키텍처 제약으로 놓고 설계해야 했습니다.

## 다음에 할 것

- **재측정**: 라우팅 수정 후 20문항 전체를 다시 측정해, 수정 전후를 숫자로 비교합니다.
- **재시도**: 처음 고른 도구가 실패하면 다른 도구로 한 번 더 찾게 합니다.
- **한도 대응**: 큰 PDF는 나눠서 임베딩하고, 한도에 걸리면 사용자에게 알립니다.
- **패키지 이전**: 지원 종료 예정인 `langchain-community`에서 독립 패키지로 옮깁니다.

## 마치며

7월에는 "돌아가는 것"을 만들었고, 11월에는 "제대로 돌아가는지 확인하는 방법"을 만들었습니다.
돌이켜 보면 이번에 고친 버그의 대부분은 측정하지 않으면 보이지 않는 종류였습니다.
그래서 다음 프로젝트에서는 기능보다 평가 세트를 먼저 만들어 볼 생각입니다.
